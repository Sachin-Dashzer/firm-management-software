# QA run of 09-11-2026 — what was done about each issue

A browser QA pass on the CRM against localhost found 36 issues. This file
records the outcome of every one: **fixed**, **intended** (it works that way
on purpose, with the reason), or **deferred** (with what it waits for).

Worked through in seven phases, in the order the issues were handed over.
Each phase has its own commit, with the full test suite and `next build`
green before it was made.

---

## Phase 1 — data loss and email (#1, #2, #15)

| #   | Outcome   | What was done                                                                                                                                                                                                                                                                                                                                                                                             |
| --- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **fixed** | Saving an edited client no longer wipes their address, and no longer blanks the fields the edit form does not show (a contact's WhatsApp number, their WhatsApp opt-out, a GSTIN's active flag). A form may now only change what it actually carried, at both levels: the sections it has, and the fields of a row it asked about. **One decision left for the owner — see below.**                         |
| 2   | **fixed** | `EMAIL_REDIRECT_TO` is now applied in exactly one place, on the send itself, so it governs every message whatever happened between queueing and posting. Both screens that talk about email carry a banner saying which mode email is in, and the message log shows both the intended and the actual recipient. The "no mailbox is configured" line no longer appears when one is configured but turned off. |
| 15  | **fixed** | An empty value renders as nothing and takes its stranded blank line with it, so no client is sent a literal `{unpricedLine}` again. A placeholder nothing filled is still left visible — but such a message is now recorded as **failed**, with the placeholder named, and is never posted by any route.                                                                                                     |

### Why #1 happened

`readClientForm()` always returned `addresses: []`. The edit form at
`/clients/[id]/edit` has no address fields, so every save of an edited client
overwrote the saved addresses with an empty list. Nothing on screen said so,
and the activity feed recorded it as `[object Object] → [object Object]`.

The same shape of bug sat one level down: the form asks a contact for a name,
a designation, a mobile and an email, and the validator normalised the fields
it was not given — a contact's WhatsApp number and opt-out — to empty.

### Why #2 happened

The test redirect was applied when a message was **queued**, in the web
process. The message is actually posted up to five minutes later, by the job
runner, which is a different process reading its own copy of the environment.
A message queued before the redirect was switched on therefore went to the
real client address anyway. That is why the message of 07-11 was redirected
and the one of 09-11 was not.

The transport was decided by the same function in both places, but at
different moments in different processes, so the screen could describe a
transport the sender was not using. The screen now also reports the transport
the last message **actually** used, read back from the message log.

### Decision needed from the owner (#1)

Addresses can be entered when a client is taken on, and can now never be
wiped — but there is still **no screen on which to correct one**. Either:

- an Addresses section is added to the client edit form, or
- correcting an address stays a job for whoever can edit the database.

Say which and it will be done. Nothing is lost either way in the meantime.

### Files changed in Phase 1

- `lib/clients/form.js` — new. Reading a client form, and what an edit of a
  stored client means. Pure, with tests.
- `app/(app)/clients/actions.js` — uses it; the form-reading helpers moved out.
- `app/(app)/clients/ClientForm.jsx` — declares its repeated sections, sends
  each row's id, and pairs each checkbox with a hidden value so unticking is
  a change the server can see.
- `app/(app)/clients/[id]/edit/page.jsx` — passes each row's id.
- `lib/clients/validate.js` — a row keeps the fields the form did not carry.
- `lib/mailer/templates.js` — `fill` and `compose`: empty renders empty,
  unfilled placeholders are reported.
- `lib/mailer/guard.js` — `redirectFor`, the one place the test redirect is
  applied; `applyGuard` no longer redirects.
- `lib/mailer/index.js` — `sendMail` applies it and reports where the message
  really went, and by which transport.
- `lib/mailer/notify.js` — a message with an unfilled placeholder is recorded
  failed, not queued.
- `jobs/sendMail.js` — records the actual recipient and transport; refuses a
  message with a placeholder left in it.
- `models/MessageLog.js` — `via` and `unfilled`.
- `app/(app)/settings/automation/actions.js` — "send again" refuses a message
  whose wording is still incomplete.
- `components/ui/MailModeBanner.jsx` — new. Test mode / live, in one line.
- `app/(app)/settings/messages/page.jsx`, `Messages.jsx`,
  `app/(app)/settings/automation/page.jsx`, `AutomationBoard.jsx` — the banner,
  the honest delivery wording, the last transport actually used.
- `tests/client-form.test.js` — new.
- `tests/mailer.test.js` — the redirect, the empty value, every template.
